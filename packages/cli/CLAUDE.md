# @savvy-web/cli

`@savvy-web/cli` provides the `savvy` binary — the unified developer-tooling CLI for the Silk Suite. Built via `@savvy-web/bundler`.

## Key surface

- Top-level commands: `init`, `check`, `commit`, `changeset`, `lint`, `clean`, `repos` (the `repos` group — vendored `.repos/` reference repos — is an intentional expansion of the original six). `repos` subcommands: `status` (`--json`, `--drift` runs `Repos.ReposDrift.check`), `sync`, `add`, `pin`, `note`, `remove`, `rename`, `restore`, `deregister` (clears a stale `submodule.<section>` local-config registration — the drift report's orphan case; local config only, so unlike the other mutating repos commands nothing is staged, there is no friendly missing-manifest exit-0, and `ReposLockdownError` is not in its union).
- `savvy repos sync`/`add`/`pin`/`remove`/`rename`/`restore` are enforcement points for the vendored-tree boundary: silk-effects' `Repos.ReposLockdown` leaves each `.repos/<name>` WORKTREE (not its gitdir) OS-level read-only after every mutation, and `sync`/`add` declare the boundary to git in local config, so `ReposGroup` provides `Repos.ReposLockdown` alongside `ReposConfigStore`/`Git`. Every handler maps each `Repos` error its `ReposManager` method can produce (`ReposLockdownError` included) to a hinted `CommandError` through `ReposCli.toCommandError` (`src/commands/repos/shared.ts`), so `reposCommand`'s hand-written error channel is `CommandError | CliError.ShowHelp | Cancelled` — never a raw `Repos` error. A name left off opens a `Select` of vendored repos at a terminal (pin/rename/note/remove; `deregister` picks stale registrations; `restore` a `MultiSelect`; `add` prompts for missing `--ref`/`--purpose`); off a terminal it stays a usage error — `ReposCli.missingArgument` raises core's `CliError.ShowHelp` carrying `MissingArgument`, so the subcommand's help prints on stderr exactly as for a parse error, exit 64 — and nothing mounts. `restore`/`remove` confirm, with `--yes`; `sync` never prompts.
- Repos handlers render outcome, not attempt: `restore` reports every `stillDirty` repo and sets exit 1 through `CliExit.set(1)`, and `remove` echoes the removed entry's `orientation` block so a re-vendor can pass it back to `add`. `sync` deliberately does NOT render `boundaryMarked` — it is re-asserted on every entry on every run, so logging it would print a line per repo on an idle sync and suppress the "up to date" line; it stays in the structured report.
- `savvy init` and `savvy check` are the sole setup/validation entry points (no per-tool init/check subcommands). `check` runs all three tools without short-circuiting and prints ONE document — a collapsible `CheckSection` per tool (`src/commands/check-section.ts`; a `::group::` under Actions), a summary, a `run savvy init` tip — and exits 1 on anything `savvy init` would fix; advisory items stay exit 0. `init` asks for `--lint-preset` at a terminal (else `silk`) and confirms `--force` only when it would overwrite; a changeset-step failure sets exit 1 but commit/lint still run (`runChangesetInit` never fails; `runChangesetInitOrFail` does).
- `savvy clean` draws a live progress view (`CliUi.live`, `src/commands/clean/view.tsx`, loaded lazily) only for a person at a terminal; every other run prints per-workspace documents. Unremovable targets fail as one `CommandError`.
- `savvy changeset` group: `lint`, `check` (validates changeset files), `transform`, `validate-file`, `version` (native version bumping via silk-effects' `Changesets.ReleasePlanner.apply` — no `changeset` shell-out, true no-write `--dry-run`), plus `config validate` and `deps detect`/`deps regen` (thin adapters over silk-effects' `Changesets.DepsRegen` — orchestration lives there, not in the CLI).
- `savvy init` writes `@savvy-web/changelog` as the canonical `.changeset/config.json` changelog id; `savvy check` still accepts the prior silk shim subpath (`@savvy-web/silk/changesets/changelog`) and the pre-merge `@savvy-web/changesets/changelog`.
- Entry split: `src/bin.ts` imports `main` from `src/main.ts` and calls it, nothing else. `main(options?: MainOptions)` runs `NodeRuntime.runMain(CliRuntime.main(CliAudience.run(rootCommand, { version }), { platform: CliPlatform, env, render: FailureLine.render, helpOnUsageError: "stderr" }))` (`@effected/cli`). `rootCommand` shares `CliAudience.flags()` (`--audience`/`--human`/`--agent`/`--ci`; `CliAudience.run` refuses a root without them at compile time). `env` builds the presentation environment once: audience (override `SAVVY_AUDIENCE`), terminal, theme, links, the prompt gate, `CliLog` (diagnostics opt-in via `SAVVY_LOG_LEVEL`), and the coloured formatter whose `formatVersion` renders `--version` through `VersionLine` (`src/internal/version-line.ts`; `CLI_VERSION` in `src/version.ts`) — customise the formatter through `env.formatter`, never a `CliColor.formatterLayer` in `platform`, which `main` would shadow. `NodeServices` is `CliPlatform` (NOT in `AppLive`); `CurrentDistribution` is provided once. `FailureLine.render(error, details)` (`src/internal/failure-line.ts`) checks `details.isCancelled`/`details.isNotInteractive` first — a quit prompt or a prompt refused off a terminal gets the kit's fixed line with no issues footer, since a prompt-fallback cancel arrives as a defect — then prints a typed failure as one line (its message, else its tag and fields) — or, for an error implementing `CliDoc`, the kit's report of its document — and a defect as the kit's `details.defaultLines` plus where to file it. `./main` is a published subpath because `@savvy-web/silk`'s carrier shim (`packages/silk/src/bin/savvy.ts`) calls the same `main()` with `{ distribution: { name: "@savvy-web/silk", version } }`, so `--version` appends `via @savvy-web/silk <version>` — silk, not this package, is what a consumer installs for the `savvy` bin, and the root `package.json` no longer devDepends on cli. `src/index.ts` (the library barrel) stays side-effect-free and never exports `main`.
- Stdout contract: stdout carries ONLY command results — human reports as `@effected/cli` documents through `Report` (`src/internal/report.ts`: `ok`/`warn`/`fail`/`skip`/`heading`/`detail`/`line`/`verbatim`/`summary` build `Doc` blocks, `Report.print` renders them for the audience — ANSI for a person, plain for an agent or a pipe, a GitHub Actions log under Actions — and never wraps off a terminal), JSON (`Console.log`), and hook envelopes (`process.stdout.write`). Read-only commands print one document; commands that write files print per completed step, so a mid-run failure still shows what was written. EVERY `Effect.log*` line, including a failure's explanation, goes to stderr — so never print a result with `Effect.log`, and never log a diagnostic with `Report`. Findings stay in the stdout document, not `CliMessage` (whose warning/failure lines go to stderr). `repos status --json` on a config error still prints `{ error, clean: false }` JSON to stdout: the gitmodules-drift monitor `JSON.parse`s it.
- Exit codes: findings exit 1 via `CliExit.set(1)`; a usage error exits 64 (`CliRuntime.main`) with the error AND the help on stderr and stdout empty (`helpOnUsageError: "stderr"`), while an explicit `--help` or a bare group invocation prints help on stdout and exits 0. NEVER touch `process.exitCode` or call `process.exit` in `src/` — `__test__/boundaries.test.ts` fails on any occurrence (`SourceBoundary` `forbidTokens: ["process.exit"]`, which also covers `process.exitCode` and `process.exit (`), confines `process.env.__PACKAGE_VERSION__` to `version.ts`, and ratchets the files that read `process` at all (add a new reader deliberately, never casually).
- Failures: fail a command with `CommandError` (`src/internal/command-error.ts`; `{ message, detail?, hint?, cause? }`, `CommandError.from(foreignError, { message, hint?, detail? })` at the edge) instead of `Effect.logError` + `CliExit.set(1)`. It implements the kit's `CliDoc`, so `FailureLine.render` hands it `details.defaultLines` (status line, muted detail, `TIP:` callout, drawn per audience); exit 1. Findings still print + `CliExit.set(1)`.
- Destructive commands: `yesFlag` (`--yes`/`-y`, default false) + `confirmDestructive({ message, yes })` (`src/internal/confirm.ts`) → `Effect<boolean, Cancelled, CliTheme>`: `--yes` or a non-interactive run proceeds without loading Ink; a person gets the kit `Confirm` screen (Enter alone = no; Esc = `Cancelled`, exit 130).
- Built-in flags: `CliConfigLive` (`src/cli/index.ts`, provided by `main()`) keeps `--help`/`--version`/`--completions`/`--log-level` and trims core's `--wizard`; `__test__/built-ins.test.ts` pins it (only an interactive run tells the trim from the kit's own wizard gate).
- Ink/React: `ink` + `react` are regular deps (`catalog:silk`), `@types/react` a devDep; tsconfig sets `"jsx": "react-jsx"`. JSX lives only in its own `.tsx` module, reached only through a dynamic `import()` on the path that draws (`clean/view.tsx` is loaded that way; `CliUi.lazy` is the other acceptable route) — never JSX or a static `ink`/`react` import in a command module. The kit widgets (`Select`, `Confirm`, `MultiSelect`, `TextInput`) load Ink themselves only when they mount. `Report` builds status items; use `Doc.*` directly for tables, sections, callouts, annotations.
- Handler tests: `__test__/utils/capture.ts` (`Capture.run` returns `{ value, stdout, stderr, exitCode }`, one stdout entry per printed document, lines joined by `\n`; `Capture.layer(stdout, stderr)` for a custom stack; `Capture.env` — a human audience on a pipe, no colour, no links — is provided by both, and on its own where a test silences logging itself; `Capture.run(effect, { audience: "human"|"agent"|"ci", githubActions? })` / `Capture.envFor(options)` pick the audience and the Actions log format; `Capture.main(effect, { audience?, tty? })` runs through `CliRuntime.main` with `FailureLine.render` and returns the real failure report + exit code), `__test__/utils/interactive.ts` (`Interactive.run(effect, CliUiTestOptions?)` forks the handler in a `CliUiTest.session` → `{ session, fiber }`; drive `session.next({ contains })` with `type("y")`/`press("enter")`, `Fiber.join(fiber)` gives the `CaptureResult`; `{ interactive: false }` + `mounts === 0` for agent/CI/pipe; colour `none` by default; one `Effect.scoped` per test) and `__test__/utils/exit.ts` (`TestExit` — a per-file `CliExit` cell, `reset()` in `beforeEach`). The built bin: `__test__/e2e/bin.e2e.test.ts` over `@effected/cli/testing`'s `CliTest`, with `FORCE_COLOR=0` pinned (colour follows Node, and `FORCE_COLOR` beats `NO_COLOR`).
- Depends only on `@savvy-web/silk-effects` within the repo (an L3 front end over the L2 engine); must NOT import `@savvy-web/silk` or `@savvy-web/mcp` (the cli↔silk↔mcp non-import invariant, held by silk's `package-layering.test.ts`).
- Kit surfaces come from `@effected/*` directly, never re-exported through silk-effects: `AppLive` builds `ToolDiscovery.layer` (`@effected/commands`) over `Workspaces.localExecLayer()` and merges `ManagedSection.layer` (`@effected/templates`); `savvy commit check` classifies with `VersioningStrategy.detect` (`@effected/workspaces`) — a value class, so `classify` is total and there is no detection error to catch.
- NO `peerDependencies` block: the Effect closure is sealed as regular `dependencies` (same posture as mcp and tsdown-plugins, #228). When adding a new `@effect/*` dep, declare its required peers as regular deps too.
- `savvy commit hook pre-commit-message` guards `git commit` AND `gh pr create`/`pr edit`, but gates per rule on `parseBashCommand`'s `kind`: `forbidden-content`/`verbosity`/`soft-wrap` are commit-body rules and run for commits only; `plan-leakage`/`closes-trailer` run for both. Do NOT "simplify" that by running every rule on both — a PR body is markdown, and `forbidden-content` denies the fence the canonical release PR body carries by design.
- Changeset inspection lives in the MCP tools, not the CLI.
- `savvy lint fmt <name>` subcommands own argument parsing and file I/O ONLY. The formatting itself lives in silk-effects (e.g. `Lint.PnpmWorkspace.formatContent`) so the CLI and the lint-staged handler cannot drift; never inline a second copy of a format step here.
- `savvy lint`/`savvy check` sync each consumer `biome.json(c)` `$schema` URL to the hand-pinned `BIOME_VERSION` const in `src/commands/lint/biome-version.ts`. On a Biome upgrade, bump it alongside `@savvy-web/silk`'s peer range and Biome asset `$schema` (see that package's CLAUDE.md).
- Load-bearing dependencies (systems#631): the `dependencies` block lists `@effected/commands`, `@effected/git`, `@effected/workspaces`, and `effect` because they satisfy `@savvy-web/silk-effects`' `peerDependencies` — that need holds independently of whether `src/` also imports each of them directly (here, all four are), so none of the four may be dropped as "unused" from a lint pass alone: removing one breaks installs at install time, not at any lint pass.
