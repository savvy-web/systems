# @savvy-web/mcp

`@savvy-web/mcp` is the spawnable `savvy-mcp` server — a tools-only MCP server (not a discovery host) exposing Silk tooling over silk-effects, Effect-native on `effect/ai`'s `McpServer` (no MCP SDK, no zod). No resource/corpus layer. An L3 front end: `@savvy-web/silk` carries its bin as a shim over `./main`. Built via `@savvy-web/bundler`.

## Key surface

- Tools (ten): seven read-only — `workspace_info` (structured workspace analysis: linked/fixed package groups + resolved registry targets), `turbo_inspect` (mode cache|graph|affected over `turbo --dry`), `changeset_inspect` (mode branch|config|classify), `changeset_validate` (validates `.changeset/` files), `changeset_preview` (non-destructive release render over `Changesets.ReleasePlanner.preview`), `changeset_deps_detect` (detects dependency drift over `Changesets.DepsRegen`), `repos_inspect` (mode status|config|drift|gitmodules over `Repos.ReposManager`/`Repos.ReposConfigStore`/`Repos.ReposDrift`) — plus three mutating tools, the sanctioned exceptions to the read-only convention: `biome_check` (runs Biome with `--reporter=gitlab`, mode check|lint, `write`/`unsafe` to apply fixes), `changeset_deps_regen` (regenerates dependency changesets over `Changesets.DepsRegen`), and `repos_manage` (action sync|pin|add|note|remove|rename|restore|deregister over `Repos.ReposManager`; its parameters are a `Schema.Union` of one struct per action, served by `@effected/mcp`'s `McpToolkit.unionTool` as a strict `oneOf` keyed by `action` and decoded by `McpToolkit.unionHandler`, so a missing field or a key the chosen action does not take is rejected as invalid parameters before the handler runs — an `isError` result naming it on `2025-11-25`/`2026-07-28`, a JSON-RPC `-32602` on `2025-06-18` — whatever `strict` says for the `Tool.make` tools; the pin result's `commitMessage` and `staleNoteIds` are the review/commit cue; `deregister` clears a stale `submodule.<section>` local-config registration — the drift report's orphan `localRegistrationDivergence` — and its description says nothing is staged, since local config is unversioned).
- `repos_manage` `sync`/`add`/`pin`/`remove`/`rename`/`restore` are also where the vendored-tree boundary is applied: `ReposManager` brackets their git mutations in `Repos.ReposLockdown` and leaves each vendored WORKTREE — not its gitdir — OS-level read-only (files `0444`, dirs `0555`), which is why `runtime.ts` provides `Repos.ReposLockdown.layer` to `ReposManager.layer` and `Repos.ReposLockdownError` is in the tool's error union. The silk plugin's guards are early warning in front of that boundary, not the boundary; `repos_inspect` is unaffected, since reading a locked tree needs no write permission. `repos_inspect` `drift` reconciles FIVE authorities (the fifth is the superproject's local git config).
- Two `repos_manage` wire details are load-bearing, since the tool description IS the agent's only instruction: `add` accepts an `orientation` object and the `remove` result carries `removedEntry.orientation`, and the description tells the agent to pass it back, because `add` resurrects nothing and remove-then-re-add is the standing remedy; and the description names what each action's result surfaces (`commitMessage`, `staleNoteIds`, `removedNotes`, what `restore` discarded), since there is no text transcript to cue the next step.
- Depends only on `@savvy-web/silk-effects` within the repo; must NOT import `@savvy-web/cli` or `@savvy-web/silk` (L3 peers never reference each other). Kit surfaces (`ToolDiscovery` from `@effected/commands`, `Workspaces`) are imported directly.
- Entry chain: `bin.ts` → `main.ts` (the `./main` subpath, `main(options?: MainOptions { distribution? })`: the whole body is `@effected/mcp/guard`'s `McpGuard.run({ label, host: process, load })` — the guard registers `uncaughtException`/`unhandledRejection` before awaiting `load`, which dynamically imports the whole server graph, so an import-time failure is reported on stderr and a rejected `load` exits 1 as `startup failed`; `main.ts`'s only static imports are the guard and an erased type, keep it that way; inside `load`, the project dir from `@effected/engine`'s `LaunchContext.projectDir` — first positional, then `SAVVY_MCP_PROJECT_DIR`, `CLAUDE_PROJECT_DIR`, cwd, skipping empty values and unsubstituted `${VAR}` placeholders; `load` returns `{ layer: ServerLayer(cwd, options), runMain: NodeRuntime.runMain }` and the guard launches it through `McpStdio.launch` with `McpStdio.teardown` — `@effected/mcp` keeps logs and launch failures on stderr and maps stdin EOF to exit 0, not 130) → `server.ts` (`ServerLayer(cwd, options?: ServerOptions)`: `McpToolkit.layer(SilkToolkit, { strict: "annotated" })` — core's `registerToolkit`, so a success is the encoded result in `structuredContent` and that same object as JSON in `content[0].text`, with no markdown or other text projection (Claude Code forwards only `structuredContent` to the model, #688; clients that display `content` see JSON, accepted); no tool is annotated `Tool.Strict`, so every `Tool.make` tool stays lenient — a deliberate, conservative default, not a response to observed client behaviour: MCP carries `_meta` at `params._meta`, which core reads separately from `arguments`, and no client-injected argument extras have been observed — `__test__/server.strict.test.ts` pins that; the union tool `repos_manage` is always strict via `McpToolkit.unionTool`; core serves `outputSchema` only for an object-rooted success schema, so the four union results (`turbo_inspect`, `changeset_inspect`, `repos_inspect`, `repos_manage`) are wrapped in `@effected/mcp`'s `ToolOutputSchema.objectRooted` (adds `type: "object"` beside the `anyOf`) and all ten tools serve one; a declared failure is `isError` text and is NOT logged; on `McpStdio.layer`, whose default protocols are `[v2026_07_28, v2025_11_25, v2025_06_18]` — the stateless adapter first, then the stateful ones; never drop the stateful ones, since `initialize`-sending clients would get `METHOD_NOT_FOUND` — plus `LogToStderr`, a `-32700` stdin guard for non-JSON lines, and `Layer.orDie`; `serverInfo.version` is `CURRENT_MCP_VERSION` plus the distribution suffix) → `toolkit.ts` (`SilkToolkit`, `ToolsLayer(cwd)`) → `tools/*.ts` (each: a `*Params` schema, a `*Result` schema that is the whole wire contract, a `Tool.make` value — or `McpToolkit.unionTool` for action-keyed params — with an explicit `dependencies` array — omit it and the handler fails `HandlersFrom` — and a `handle*` handler). `src/index.ts` never exports `main`. Re-check the `server.ts` header's gotchas (4 and 5 are now handled by `McpStdio`) on every rc bump. `__test__/boundaries.test.ts` (`SourceBoundary`): only `main.ts` touches `process` (allowed wholesale), `version.ts` is waived for the single `process.env.__PACKAGE_VERSION__` token through `allowRules`, and `bin.ts` may not touch `process` at all.
- Errors (`errors.ts`): `McpToolError = Schema.Union([WorkspaceNotFound, EngineError, BiomeFailed, ToolRefusal])`. The three local members are `Schema.TaggedError`s that spread `@effected/mcp`'s `ToolFailure.fields` and carry a field of their own (`cwd`, `source`, `exitCode`); a refusal with nothing beyond its message (a bad argument, a path escaping the workspace, a missing Biome binary) is the kit's `ToolRefusal`, built with `ToolRefusal.refuse(reason, remediation)`. `InvalidArgument`/`invalidArgument` and `BiomeUnavailable` are gone from the barrel — do not re-add them. A typed failure reaches the wire as `isError` text only (no `structuredContent`), so each `message` is composed at construction via `ToolFailure.message`, echoed caller values pass through `ToolFailure.truncate`, and `mapEngineError` is the engine-to-wire mapping every handler applies. The barrel no longer exports `Remediation`, `composeRemediatedMessage` or `truncateEchoed`.
- The runtime (`runtime.ts`, `makeSilkRuntimeLayer(cwd)`) is built once per process: the kit graph is `Workspaces.layerWithGitAndConfigDependenciesSubprocess({ cwd })` — `Workspaces.layerWithGit`'s service set with config-dependency hook replay in catalog assembly, so hook-injected catalogs resolve to their declared ranges in `changeset_deps_detect`/`changeset_deps_regen` diffs instead of concrete lockfile versions (#539); `ToolDiscovery.layer` over `Workspaces.localExecLayer({ cwd })` gives ONE probe cache for the server's whole lifetime, and the same lifetime holds one `DepsRegen`/`ConfigInspector` — which is why config caches are refreshed per call rather than per layer build (#229).
- Test tiers: `__test__/*.test.ts` run in-process over `@effected/mcp/testing`'s `McpHarness` — `__test__/utils/harness.ts` is only a thin `makeHarness(cwd, { serverLayer?, protocol?, ... })` wrapper that provides `PlatformWithoutStdio` (`NodeServices.layer` minus its `Stdio`, which would otherwise shadow the harness's queue-backed one and hang every wait); there is no hand-ported harness. `server.test.ts` asserts `content[0].text` parses to exactly `structuredContent` for struct- and union-rooted tools across protocol revisions, the served `oneOf` for `repos_manage`, and the invalid-params split by revision; `server.harness.test.ts` covers the `-32700` stdin guard, the distribution suffix, lenient tools; `__test__/e2e/server-lifecycle.e2e.test.ts` spawns the built `dist/dev/pkg/bin/savvy-mcp.js` through the kit's `McpProcess`/`McpProbe` and asserts a well-formed handshake, the JSON text channel, EMPTY stderr (including across a declared failure), the `${CLAUDE_PROJECT_DIR}`-placeholder skip, and exit 0 on stdin close. Closing stdin right after a `tools/call` drops the answer and still exits 0 — read the response first.
- NO `peerDependencies` block: the Effect closure is sealed as regular `dependencies` (same posture as cli and tsdown-plugins, #228). When adding a new `@effect/*` dep, declare its required peers as regular deps too.
- Load-bearing dependencies (systems#631): the `dependencies` block lists `@effected/commands`, `@effected/git`, `@effected/workspaces`, and `effect` because they satisfy `@savvy-web/silk-effects`' `peerDependencies` — that need holds independently of whether `src/` also imports each directly, so none may be dropped as "unused" from a lint pass: removing one breaks installs at install time.
