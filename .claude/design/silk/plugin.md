# plugins/silk — merged Claude Code plugin

The `silk@savvy-web-systems` Claude Code plugin. Merges the skills, agents and hooks of the three source plugins (changesets, commitlint, lint-staged) into one, repointed at the unified `savvy` bin, and adds a read-only Turborepo capability (the `turbo` skill and `turborepo` agent) and a Biome capability (LSP plus the `biome_check` MCP tool) over the shared `savvy-mcp` server.

## Overview

`plugins/silk` is the companion plugin for `@savvy-web/silk`. It is **authored and bundled** in this monorepo (plugins are static, not runtime-discovered) and registered as a **local** entry in `.claude-plugin/marketplace.json` (`source: "./plugins/silk"`).

- **Location:** `plugins/silk` in `savvy-web/systems`
- **Marketplace name:** `silk@savvy-web-systems`

## Current State

Implemented. Contents:

- **Skills** (`plugins/silk/skills/`): the merged set — tool-prefixed user-facing skills plus unprefixed internal mechanics. See the directory listing for the authoritative set and [Skill naming scheme](#skill-naming-scheme).
- **Agents** (`plugins/silk/agents/`): `changeset-manager.md`, the only caller of the unprefixed internal skills; `turborepo.md`, the Turborepo domain agent that drives the MCP `turbo_inspect` tool for multi-step cache diagnosis, `turbo.json` refactors and CI cache setup; and `tsdoctor.md`, the TSDoc agent that drives a package's `ae-*`/`tsdoc-*` diagnostics to zero off the build's `issues.json` artifact. See [Turborepo capability](#turborepo-capability) and [TSDoc capability](#tsdoc-capability). Every agent declares a curated `tools:` allowlist (never omit `tools:` — inheriting everything undoes the scoping), and every allowlist must include `SendMessage`: a teammate-dispatched agent without it cannot report back or answer a `shutdown_request` and idle-loops until killed (savvy-web/systems#256, #263).
- **Turbo skill** (`plugins/silk/skills/turbo/`): the model-invocable `turbo` front-door skill, self-contained via bundled `references/` — the six Turborepo standards that used to be served from the mcp corpus now live there. See [Turborepo capability](#turborepo-capability).
- **Build skill** (`plugins/silk/skills/build/`): the model-invocable `build` authoring reference (`/silk:build`, also `paths`-triggered on `**/savvy.build.ts`) for the `@savvy-web/bundler` / `@savvy-web/rspress-builder` / `@savvy-web/tsdown-plugins` toolchain, self-contained via bundled `references/`. It shares the `**/savvy.build.ts` auto-load path with the `tsdoc` skill by design: `build` owns build *config*, `tsdoc` owns doc *comments*.
- **TSDoc capability** (`plugins/silk/skills/tsdoc/`, `agents/tsdoctor.md`, `plugins/silk/monitors/`): the skill, the `tsdoctor` agent and a background monitor over the build's `issues.json` artifact. See [TSDoc capability](#tsdoc-capability).
- **Vendored-repos capability** (`plugins/silk/skills/repos/`, `hooks/session-start/repos-orientation.sh`, three `pre-tool-use/repos-*-guard.sh` hooks): the judgment-layer skill for `.repos/` (vendored read-only reference repos over `@savvy-web/silk-effects`' `Repos` namespace, the `savvy repos` CLI group and the `repos_inspect`/`repos_manage` MCP tools), an always-on SessionStart orientation block, and three PreToolUse guards denying direct mutation of vendored trees. The guards are the early-warning UX in front of the real boundary, which is OS-level: `Repos.ReposLockdown` chmods vendored trees read-only. See [Vendored-repos capability](#vendored-repos-capability).
- **Dogfood-mailbox capability** (`plugins/silk/skills/dogfood/`, `hooks/pre-tool-use/dogfood-guard.sh`, `monitors/dogfood-mail.mjs`): the cross-repo agent-collaboration protocol — a mode-driven skill, an enforcement guard and the plugin's second background monitor. See [Dogfood-mailbox capability](#dogfood-mailbox-capability).
- **it2 pane-orchestration capability** (`plugins/silk/skills/it2/`, the gated `<terminal>` sub-block in `hooks/session-start/orientation.sh`): a self-contained iTerm2 pane-orchestration skill plus a conditionally-rendered orientation nudge. The lightest capability shape — a skill and a gated orientation block, no agent, MCP tool or guard. See [it2 pane-orchestration capability](#it2-pane-orchestration-capability).
- **Hooks** (`plugins/silk/hooks/`): all three source hook sets merged into one `hooks.json` plus per-event script dirs and a shared `lib/`. See [Hook merge](#hook-merge).
- **MCP wiring**: an `mcpServers` block in `.claude-plugin/plugin.json` spawns the shared `savvy-mcp` server via `bin/start-mcp.sh`, and the always-on `session-start/orientation.sh` hook orients the agent toward the server's tools. This is the "direction" half of the information-vs-direction split — see `../mcp/architecture.md` and [MCP tool orientation](#mcp-tool-orientation). The sibling `plugins/github-actions` reuses the identical launcher and server declaration.

## Skill naming scheme

The naming scheme is the load-bearing convention; the exact skill list is discoverable in the `skills/` directory.

- **User-facing skills are tool-prefixed** (the `changeset` router plus its `changeset-style`/`changeset-config` siblings, and `commit-create`; `pr-body` is the one message-authoring skill named for its document rather than its tool, because no tool owns a PR description). Prefixing disambiguates now that three tools share one plugin. Capability skills are named for their capability (`build`, `tsdoc`, `turbo`, `repos`, `dogfood`).
- **Internal mechanics stay unprefixed** (`config`, `dependencies`, `update`, `merge`, `delete`, `status`). They are not user-invoked — only the `changeset-manager` agent calls them by name, so they keep their short names.

## Changeset command surface

The changeset user surface is a single flag-driven router skill, `changeset` (`/silk:changeset --create|--squash|--list|--preview|--check`), that replaced five former per-command skills (`changeset-create`, `changeset-squash`, `changeset-check`, `changeset-list`, `changeset-preview`). The router parses the leading flag and dispatches; everything after it passes through verbatim. See `skills/changeset/SKILL.md` for the authoritative dispatch table.

- `--create` / `--squash` → the `changeset-manager` agent (`subagent_type: silk:changeset-manager`), in create or squash mode.
- `--check` → the `changeset_validate` MCP tool directly (typed CSH001–CSH005 diagnostics, no CLI script).
- `--preview` → the `changeset_preview` MCP tool directly (see [The config skill drives changeset_inspect](#the-config-skill-drives-changeset_inspect)).
- `--list` → the bundled `scripts/list.sh`, moved here from the old `changeset-list` skill.
- A bare or vague invocation defaults to create/reconcile; a phrase table maps auto-triggered wording to a mode.

The router declares a **scoped** `allowed-tools` (`Agent`, `changeset_validate`, `changeset_preview`, `Bash(bash *)`) — it holds only the grants its own modes fire directly. The heavier `changeset_inspect` and `changeset_deps_*` grants live on the `changeset-manager` agent it dispatches to, not on the router.

Two changeset skills stay separate from the router because they cover file formats, not commands: `changeset-style` owns `.changeset/*.md` body format, and `changeset-config` owns `.changeset/config.json` — including the Silk-custom per-package `versionFiles` and `additionalScopes` fields (both auto-load on their respective paths).

## MCP tool orientation

The silk plugin spawns the shared `savvy-mcp` server (tools-only — see `../mcp/architecture.md`) and orients the agent toward its tools. The combined `hooks/session-start/orientation.sh` hook (see [Hook merge](#hook-merge)) emits a single always-on `<silk_capabilities>` block, deliberately **compact and index-shaped** since the 2026-07 context-engineering trim (which cut the emitted payload by more than half without changing the block tag structure, so the bats payload assertions held): a one-line-per-tool `<mcp_tools>` index closing with a pointer that parameter and mode detail lives on each tool's schema, a one-sentence `<agents>` index naming changeset-manager/turborepo/tsdoctor plus the proactive-dispatch nudges (changeset-manager when implementation work concludes, tsdoctor the moment a build reports API Extractor issues), a `<skills>` name list deferring descriptions and auto-load triggers to the skills listing, a three-line `<biome>` division of labor, a **conditionally-rendered** `<terminal>` sub-block (see below), and a short prose `<active_hooks>` note (guards cover commit/PR messages, `.repos/**` writes, dogfood-linked pushes and changeset validation; a deny explains itself; the Stop-time note is for the user; never work around a hook). The old imperative "USE THEM" / "Do not infer X" litany is now one judgment-framed sentence — a structured answer from a tool beats one reconstructed from shell stdout or memory, with Bash as the escape hatch.

**The `<terminal>` sub-block is the one payload entry that is conditional.** Every other entry renders on every start; the `<terminal>` block renders only when a cheap, prompt-free gate holds — the session is in iTerm2 (`TERM_PROGRAM == "iTerm.app"` OR `LC_TERMINAL == "iTerm2"`) AND the `it2` CLI is on `PATH`. The gate runs no it2 subprocess (the hook fires on every resume/compact and must never trigger it2's first-use iTerm2 API-authorization dialog or hang — see [it2 pane-orchestration capability](#it2-pane-orchestration-capability)); a non-iTerm session pays no `<terminal>` payload at all. When it renders, the block is a proactive pane-orchestration nudge — split and badge a pane per subagent, manage the user's windows legibly, match layout to window geometry, and a dismiss-and-close discipline (shut down subagents you no longer need and close their panes; leave no idle agents or orphaned panes) — that points at the `/silk:it2` skill for the layout playbook. It stays index-shaped; the depth lives in the skill.

The trim's rule, recorded in the hook's header comment, is that duplicated or on-demand-loadable detail does not belong in an always-on payload that re-fires on resume/compact: per-tool mode/parameter detail duplicated the tool schemas (which load on demand), per-skill descriptions duplicated skill frontmatter, and full agent scope descriptions duplicated the agent listing. The payload still advertises every skill and both background monitors (`tsdoc-diagnostics`, `dogfood-mail`); per-capability depth lives at point-of-use — the path-triggered `changeset-style`/`build`/`tsdoc` skills, the on-demand `turbo`/`repos`/`it2` skills, and the PreToolUse nudges. The hook has no matcher, so it fires on every start including resume/compact; only the `<terminal>` sub-block within the always-on payload is conditional (see above). The companion trims — a judgment-toned rewrite of `startup-only.sh`'s blocks, progressive-disclosure splits of the `dogfood`/`commit-create` skills and the `changeset-manager` agent — are tracked in savvy-web/systems#392 and not yet shipped.

This is the "direction" half of the information-vs-direction split: information lives in the server, direction in the plugin.

## Turborepo capability

The plugin layers a read-only Turborepo capability over the shared `savvy-mcp` server's `turbo_inspect` tool (see `../mcp/architecture.md`), structured as a light always-on nudge, an on-demand skill and a domain agent for heavy work.

- **Orientation.** Since the 2026-07 trim, the `<silk_capabilities>` payload indexes `turbo_inspect` in one line — cache/graph/affected inspection, read-only, never runs tasks — with mode and parameter detail deferred to the tool's schema, and names the `turborepo` agent and `/silk:turbo` skill in the agent/skill indexes. `turbo_inspect` has **no** hook — it is a read-only MCP tool the agent calls directly.
- **The `turbo` skill** (`skills/turbo/SKILL.md`) is the model-invocable front door: decision trees, an anti-pattern catalog with rationale, and bundled `references/` deep dives (the six Turborepo standards previously served from the mcp corpus). It encodes the Silk install/build-decoupling turbo ordering so recommendations respect the monorepo's CI order.
- **The `turborepo` agent** (`agents/turborepo.md`) is the autonomous specialist for heavier work, operating in three modes (cache diagnosis / graph refactor / affected-CI). Its contract is *diagnose first, recommend second*: it pulls actual hash contributors and graph edges via `turbo_inspect` and only edits `turbo.json` once it can cite the contributor that justifies the change. It preloads the `turbo` skill.
- **Safe-bash allowlist.** `hooks/lib/safe-bash-patterns.txt` auto-allows read-only `turbo … --dry`/`--dry=json` runs. The bare `turbo run <task>` form (which executes the task and mutates the cache) is intentionally **not** allowlisted — the load-bearing safety line that keeps the capability read-only at the bash layer too.

## Biome capability

The plugin gives the agent three channels onto Biome — the suite's linter/formatter — each suited to a different intent: automatic in-loop feedback (LSP), on-demand structured execution with fixes (the MCP tool), and a narrowly-sanctioned Bash path (the three root lint scripts only — Bash Biome is otherwise denied, not an escape hatch). The plugin only wires the connections; both the LSP and the MCP proxy require Biome on `PATH` (the suite uses a global Biome, matching the VS Code extension) — neither bundles the binary.

- **The Biome LSP — automatic diagnostics.** An `lspServers.biome` block in `.claude-plugin/plugin.json` (same shape as the `mcpServers` block) launches Biome's language server so lint/format diagnostics on the file the agent just edited land in context with zero prompting. The `command` is `sh` running `bin/biome-lsp.sh`. The `extensionToLanguage` map covers the suite's source extensions but deliberately omits html (the suite has none); see the `lspServers.biome` block in `plugin.json` for the authoritative list. The LSP is diagnostics-only: it sees only open/edited files (not a whole-repo scan) and **cannot apply fixes** — fixing is the MCP tool's or Bash's job.
- **`bin/biome-lsp.sh` — the resolver.** A POSIX `sh` wrapper (skeleton of `bin/start-mcp.sh`, `set -eu`, `exec`s the final process) so a consumer without a global Biome gets an actionable error instead of a bare `Executable not found in $PATH`. Resolution order matches `Lint.Biome`'s own discovery: global `biome` on `PATH` first, then a walk-up for project-local `node_modules/.bin/biome`, then a clear stderr message and a non-zero exit.
- **`biome_check` MCP tool — structured execution with fixes.** The shared `savvy-mcp` server exposes a `biome_check` tool that runs Biome over a path and returns parsed diagnostics, supporting read-only check plus safe (`write`) and unsafe (`unsafe`) fixes. This is the "I want a structured result or want to apply fixes" channel the LSP cannot provide. See `../mcp/architecture.md` for the tool (it is the first mutating savvy-mcp tool, an intentional read-only-convention exception).
- **The `biome-prefer-mcp` PreToolUse hook — nudge, never block.** `hooks/pre-tool-use/biome-prefer-mcp.sh` (a second `matcher: "Bash"` PreToolUse entry in `hooks.json`, right after `commit-bash.sh`) detects when the agent runs Biome through Bash — either directly (Biome in *command position*) or indirectly via a package-manager/turbo script whose nearest `package.json` body mentions `biome` — and emits a one-time-per-session `additionalContext` nudge toward `biome_check`. It is **purely additive**: it emits **no** `permissionDecision`, so a command it inspects always proceeds on its own account. That is this hook's own contract, not Bash Biome's posture as a whole — a separate hook, described next, denies every route to Bash Biome except three sanctioned scripts, so "Bash Biome is a valid escape hatch" is not true at all outside those three. The once-per-session marker keys on the envelope `session_id` under `~/.claude/session-env/`, falling back to a fixed `_no-session` key when no session id is present. It fails open without `jq` and is best-effort on the indirect case (only the nearest root `package.json` is consulted). The MCP proxy and the LSP both run Biome in their own processes (not the Bash tool), so neither self-triggers the hook. Two boundary rules keep the nudge from misfiring:
  - **Subagent suppression (savvy-web/systems#247).** The envelope carries `agent_id` only inside a dispatched subagent call, and subagents run with an explicit curated `tools:` allowlist — so a session-level "prefer `biome_check`" nudge is either redundant (the subagent already lists the tool) or a dead end (it lacks the tool, gets "No such tool available", falls back to Bash Biome and re-triggers the hook, a loop with no exit). The hook emits nothing when `agent_id` is present, and does so *before* touching the once-per-session marker so a subagent's Bash Biome call never consumes the main thread's one-time nudge. The main-session nudge (no `agent_id`, tool genuinely available) is unchanged.
  - **Command-position matching (savvy-web/systems#248).** Biome counts as invoked only when it is the first token of a control-operator-delimited segment (quote-aware, so an operator inside a quoted argument is not a false boundary; optionally path-prefixed, and after peeling a leading `env`, inline `VAR=value` assignments and/or a runner keyword like `npx`/`pnpm run`) — not when "biome" merely appears as a later argument or inside quoted prose (the `gh issue create --body "…biome…"` false-fire this fixes). It is deliberately not a full shell parser: command substitutions are not descended into, a false-negative-over-false-positive choice consistent with "a nudge, not a parser".
- **The `biome-direct-deny` PreToolUse hook — deny, not nudge.** `hooks/pre-tool-use/biome-direct-deny.sh` (a third `matcher: "Bash"` PreToolUse entry in `hooks.json`, immediately after `biome-prefer-mcp.sh`) denies EVERY direct route to Biome except the three sanctioned lint scripts — `lint` / `lint:fix` / `lint:fix:unsafe` — run through any of pnpm/yarn/bun/npm, bare or `run`-prefixed. It supersedes this hook's earlier incarnation (`biome-npx-deny.sh`, which denied only `npx biome`/`bunx biome`); the user reversed the default after reviewing that narrower hook's coverage. Two reasons: `biome_check` returns typed diagnostics an agent doesn't have to parse, and — the load-bearing reason — a direct invocation does not resolve the repo's config (`packages/silk/public/biome/silk.jsonc` excludes `!**/.repos` and `!.claude/worktrees`, which the root `biome.jsonc` extends), so it walks straight into `.repos/**` read-only vendored submodules and can corrupt them. The three sanctioned scripts are safe by construction — they run from the repo root through `package.json`, so the config always resolves. Every other route is denied now, including forms that resolve REAL Biome: `npx @biomejs/biome` / `bunx @biomejs/biome` were the old hook's one deliberate carve-out (real Biome, not the `0.3.3` impostor at savvy-web/systems#380); that carve-out is reversed here, since real Biome without the repo config is exactly the corruption hazard. Every package-manager script is left alone, sanctioned name or not, bare or decorated — `pnpm --filter @savvy-web/cli lint`, `pnpm -r lint`, `turbo run lint` all allow, since a script invocation resolves `package.json` (and, for a workspace-scoped or turbo-task form, the workspace graph) before anything runs, so it always carries the repo's Biome config regardless of which script name or flag reaches it. An earlier version of this hook on this branch ALSO denied any package-manager script other than the three sanctioned names, as an "accepted consequence" of a stricter reading — probing that version showed it was backwards against the actual hazard (config-less DIRECT invocation): it blocked decorated forms of the sanctioned names while letting every OTHER script name through unexamined. Building a hazard-accurate version of that check would mean resolving package.json scripts and the turbo task graph, machinery this hook does not have; an approximate DENY is worse than an approximate nudge (a missed nudge is a lost hint, a false deny blocks legitimate work — the exact failure class savvy-web/systems#387 needed four fix rounds to eliminate). So that check was removed rather than made hazard-accurate: one rule, no exception, no heuristic — deny only what is directly, syntactically verifiable as reaching the biome binary. Coverage of that one rule is keyed to the SCRIPT NAME across all four package managers, not to this repo's own package manager, since an agent that cannot run `biome` reaches for whichever runner is available. A deny from this hook is authoritative even when `biome-prefer-mcp.sh`'s nudge also fires on the same command; the two stay separate hooks with separate contracts (nudge-only vs. deny) precisely so this behavioral gate never compromises the nudge hook's purely-additive guarantee. Both hooks share `hooks/lib/split-segments.sh` for quote-aware, control-operator-aware command segmentation and prefix peeling (env / VAR=value / sudo / command / time / exec / npx / bunx / the two-token `bun x` and `pnpm dlx`/`yarn dlx` aliases / pnpm|npm|yarn|bun\[ run\], reduced all the way to the invoked binary): splitting into command-position segments first, rather than one giant regex over the raw command string, means each hook only has to recognize its target shape at the start of an already-isolated sub-command. There is no longer a separate "neutral" peel mode that leaves `npx`/`bunx` unpeeled — that existed only so the pre-reversal deny hook could exempt the scoped `@biomejs/biome` package by matching the literal token immediately after `npx`/`bunx`; now that the scoped package is denied too, both hooks fully peel to the invoked binary and rely on the bare-biome match's path-prefix group to catch `@biomejs/biome` the same way it already catches `/usr/local/bin/biome`.
- **The `<biome>` orientation block.** `hooks/session-start/orientation.sh` carries a `<biome>` block: the LSP reports diagnostics on edited files automatically; `biome_check` covers wider checks and every fix pass; direct Bash Biome is DENIED (any route — bare, path-prefixed, exec, npx/bunx/dlx, sudo/env-wrapped) except `pnpm`/`yarn`/`bun`/`npm` `lint`, `lint:fix`, `lint:fix:unsafe` at the repo root, since a direct invocation skips the repo config and can corrupt `.repos/**` vendored submodules. The full division-of-labor teaching — including the never-run-Biome-just-to-look rule and the sanctioned-script list — lives only in `startup-only.sh`'s `<running_tools>` preference order.

## TSDoc capability

The plugin's TSDoc capability mirrors the Turborepo shape — a reference skill, a domain agent and an always-on surface — all built on the structured `dist/<target>/issues.json` artifact `@savvy-web/tsdown-plugins` emits (see `../tsdown-plugins/architecture.md`). It is the agent-facing half of the binary `@public`/`@internal` release-tag and API-Extractor-diagnostic policy that package enforces in code; the policy it teaches is the same one `runApiExtractor` routes and escalates (which fails CI on forgotten exports).

- **The `tsdoc` skill** (`skills/tsdoc/SKILL.md`) is the model-invocable authoring reference (`/silk:tsdoc`, also `paths`-triggered on `**/savvy.build.ts` and `**/dist/*/issues.json`) plus bundled `references/`. It teaches toolchain-correct TSDoc and the binary release-tag recipe. Its "Verify your work" step now reads `dist/prod/issues.json` (a `jq` filter on `ae-*`/`tsdoc-*` codes) rather than grepping build stdout — keying off the artifact's contract that an absent file means not-built and a present-but-empty file means clean. **That second half is now only true when the artifact's `buildOk` is `true`:** the artifact is written on the failure path too, so a crashed build leaves empty buckets that read as a clean gate (see `../tsdown-plugins/architecture.md`). The skill's `jq` filter and the `tsdoctor` agent's read step do NOT yet inspect `buildOk` — an adoption gap, not a design change; both should gate on it, and the skill's "a present file with empty warnings/errors means clean" sentence needs the qualifier.
- **The tsdoc skill's authoring rules extend to transcription, not just tags.** Beyond the diagnostic-to-fix table, the skill now rules that a verbatim source transcription inside a doc block (a type alias, a config object, a generic like `MapLike<T>`) belongs in a fenced `ts` code block rather than backslash-escaped: TSDoc does not parse fenced contents, so braces and angle brackets pass through, whereas escaping each one is both unscalable and the wrong mental model of why `tsdoc-escape-right-brace`/`tsdoc-escape-greater-than` fired. The general shape of every rule in this skill — name the diagnostic, name the fix, explain the parser reason — is what keeps it a reference rather than a checklist.
- **The `tsdoctor` agent** (`agents/tsdoctor.md`) drives a package's diagnostics to zero end to end: build (prod, because `ae-*`/`tsdoc-*` come from the prod-only meta pass) → read `dist/prod/issues.json` → fix each `ae-*`/`tsdoc-*` per the skill's binary release-tag policy → rebuild to confirm clean. It preloads the `tsdoc` skill and edits only source TSDoc and the export/release-tag surface. Its load-bearing boundary: it **never adds `suppressWarnings` entries** — suppression is a human escape hatch — and it surfaces a genuine `@beta`/`@alpha` maturity call to the user rather than guessing.
- **The background monitor** (`monitors/monitors.json` + `monitors/watch-issues.mjs`) is a Node poller that surfaces `ae-*`/`tsdoc-*` counts from `dist/*/issues.json` as agent notifications. It is low-noise via **debounce** (savvy-web/systems#248): a non-zero count must hold unchanged across a short quiet period (`STABLE_POLLS`, default 3 polls at the 2s interval ≈ 6s, overridable via `SILK_TSDOC_MONITOR_STABLE_POLLS`) before it notifies. A build in progress keeps the count moving and resets the streak, so the churn an agent produces while actively fixing diagnostics — or a fresh package building from scratch — never fires; a genuinely stuck non-zero count still surfaces exactly once, and a return to zero clears the dedup so a later regression can fire again. `--once` mode reports immediately (no polling history to build a quiet period from). The notification tells the reader to let an in-flight build or fixing agent finish before dispatching another, rather than acting on the line immediately. The pure `diagnose` step is an exported function so tests can import it, and the run loop is guarded by a symlink-safe entry check (`realpathSync` comparison of `process.argv[1]` against the resolved module path) so a symlinked plugin root does not silently stop the monitor from starting. This was the plugin's first background monitor and is the template the `dogfood-mail` monitor follows (see [Dogfood-mailbox capability](#dogfood-mailbox-capability)). The producing side now writes the artifact atomically (tmp + rename), so a poll landing mid-build reads the previous complete artifact rather than a torn file — the debounce covers *stale* counts, the atomic write covers *partial* ones; they are complementary, not redundant. Like the skill, this monitor does not yet consult `buildOk`, so a crashed build currently reads to it as a return to zero.
- **Why a monitor, not a hook.** A `FileChanged` hook was rejected: its matcher is literal-filename only (no glob across packages) and it injects no context, so it cannot tell the agent *which* package regressed. A background poller is the primitive that can both watch every package's artifact and emit an actionable notification naming the package and pointing at the `tsdoctor` agent / `/silk:tsdoc`.

## Vendored-repos capability

The plugin's fourth capability layers over `@savvy-web/silk-effects`' `Repos` namespace (manifest at `.repos/config.json`, git submodules under `.repos/`): a judgment-layer skill, an always-on SessionStart orientation block, and three PreToolUse guards that keep direct edits out of the vendored trees. Mutation is meant to happen only through the `repos_manage` MCP tool or `savvy repos`, never through raw `Write`/`Edit`/`Bash`/MCP-git calls — the guards exist to catch the latter, not to replace the former.

**The enforcement split is the thing to hold onto: the boundary is OS permissions, the guards are UX.** `Repos.ReposLockdown` (in silk-effects, applied by `repos_manage`/`savvy repos` `sync`/`add`/`pin`) chmods every vendored worktree — files `0444`, directories `0555` — plus the submodule's git metadata directory, and re-locks even when the triggering operation fails partway through; see `../silk-effects/architecture.md#vendored-repos-repos-namespace`. That layer, not any hook, is what actually stops a write, and it holds for every shape a pattern-matching guard misses. The plugin's guards exist because an `EACCES` deep inside a tool call is a *bad* teaching signal: the agent learns "permission problem", reaches for `chmod`, and works around the boundary instead of using the tool. A deny fires earlier, names the operation, and points at the sanctioned path. Neither layer substitutes for the other — do not "simplify" by deleting the guards on the grounds that permissions cover it, and do not tighten a guard into an approximate sandbox on the grounds that it is the only defense.

- **The `repos` skill** (`skills/repos/SKILL.md`, `/silk:repos`, also `paths`-triggered on `**/.repos/config.json`) is the judgment layer: when vendoring a repo is the right call versus training-data recall or a fork, sparse-checkout discipline, the re-pin-on-dependency-bump rule, and the notes-vs-orientation editorial policy (notes are ephemeral and ref-stamped, capped at 10 per repo; orientation's `layout`/`startHere`/`keyPaths` are durable and version-independent; a note that survives a re-pin gets promoted). It defers wire-format detail to `repos_inspect`/`repos_manage` rather than restating the schema. Its description and triggers also claim plain **git-submodule vocabulary** aimed at `.repos/` ("add a submodule", "remove a submodule", `.gitmodules`), since this skill — not raw `git submodule` — is the sanctioned path for that vocabulary in this repo. Three teachings on it are behavioral, not editorial: verify a pin with `git rev-parse HEAD` inside the checkout against `git ls-files -s .repos/<name>` and never with `git describe --tags` (in a monorepo upstream that resolves to a sibling package's tag as often as the library's own, which reads as false drift); an `EACCES` inside `.repos/**` means *use the tooling*, never `chmod` the tree back (a hand-unlock survives only until the next `sync`/`pin` re-locks it out from under you); and `sync` leaves a dirty checkout's *content* untouched while still re-locking its permissions, so "untouched" covers content only.
- **`session-start/repos-orientation.sh`** — a third, unmatched SessionStart hook (see [SessionStart hooks](#sessionstart-three-hooks-split-by-responsibility)) — is the informational half. On every start it resolves the project dir from the envelope's `cwd` (worktree-correct), and if `.repos/config.json` exists it runs `savvy repos sync` as a best-effort side effect behind an internal watchdog (`SILK_REPOS_SYNC_TIMEOUT`, default 6s, comfortably under the hook's own 10s `hooks.json` timeout) that reaps the sync process **and** every process it spawned (a `pgrep -P` snapshot taken before the kill, since an exited process's children are immediately reparented and become unreachable afterward) so no orphan can hold open a captured stdout/stderr fd and hang the caller. Sync outcome never gates the context block — a failed or timed-out sync still renders the manifest, with a one-line warning that content may be stale, because that is exactly when the warning matters most. The block is budgeted at 2000 chars: per-repo entries render in full (ref, purpose, orientation, notes) in manifest order until the next one would exceed budget, then that repo and everything after it collapses to a one-line `- <name> — <purpose> (details: repos_inspect mode:"config")` form.
- **The three PreToolUse guards are early warning, not the security boundary** — the header comment in each script says so explicitly and names `ReposLockdown` as the actual backstop. The design intent is "deny what visibly resolves to a `.repos/**` write, document the misses, point at the sanctioned tool"; the misses are acceptable precisely because the permissions layer covers them. All three share the pattern: fail open on missing `jq` or a malformed envelope, deny only, never allow. Only `repos-fs-guard.sh` and `repos-bash-guard.sh` carve out an exemption for `.repos/config.json` (the one hand-editable file — same file the `repos_manage action:"note"` MCP write targets, so a direct edit and a tool-mediated edit reach the same exemption). `repos-mcp-guard.sh` has no such carve-out: it denies any listed write-op whose stringified input contains `.repos/` at all, config.json included — conservative by design, since an MCP git/file write op is a coarser signal than the fs/bash guards' precise path match.
  - **`repos-fs-guard.sh`** (`matcher: "Write|Edit|NotebookEdit"`) is the **precise leg**: it resolves `tool_input.file_path`/`notebook_path` (absolute or relative-to-project-dir) to an exact path and compares it against `${PROJECT_DIR}/.repos/**`, with an exact-string carve-out for `.repos/config.json`. This is the first real caller of `emit_deny` (`hooks/lib/hook-output.sh`) — previously defined but unused.
  - **`repos-bash-guard.sh`** (`matcher: "Bash"`) pattern-matches the command string rather than parsing it, and documents its accepted misses up front: a `cd .repos/x` in an earlier call followed by a bare relative write in a later one, runtime-built paths via command substitution or variable indirection, and a script invoked by path that writes into `.repos/**` internally. It splits into a **git leg** — denied unless the extracted subcommand is in the read-ops allowlist (`hooks/lib/repos-git-read-ops.txt`: `status`, `log`, `diff`, `show`, `ls-files`, `ls-tree`, `cat-file`, `blame`, `grep`, `remote`, `rev-parse`, `describe`) — and a **non-git leg** covering the write-shaped commands (redirection, `tee`, `sed -i`/`--in-place` including reordered flags, `cp`, `mv`, `rm`, `patch`, `dd of=`). Both legs share `_repos_exempt`, an exact-token peel (glued redirect operator, `dd`'s `of=`, one pair of surrounding quotes) ending in an exact `.repos/config.json` compare — not a substring strip, so `.repos/config.json.bak` isn't wrongly waved through. Unlike `biome-prefer-mcp.sh`, it does **not** exempt subagent calls — a deny here holds inside a dispatched subagent's Bash call too.

    The guard was rewritten for **precision over reach** once `ReposLockdown` became the boundary: with permissions doing the enforcing, an over-deny is the expensive failure (it blocks legitimate work and teaches agents to route around hooks), so the rewrite bought accuracy with rules that each cost some theoretical coverage.

    - **Every leg matches a derived `SCAN`, never the raw command.** Two passes build it. First an awk state machine deletes heredoc bodies — intro line through the delimiter line, `<<-` tab-stripping honored, re-arming for multiple heredocs — so prose in a payload (`cat >> notes.md <<'EOF' … rm -rf .repos/x … EOF`) can't trip the guard; here-string `<<<` operators are masked (length-preserving) before intro-matching so the trailing `<<` of a `<<<` isn't read as a never-closing heredoc that swallows the rest of the command. Then a sed pass drops quoted segments containing whitespace — prose like `--body "run rm -rf .repos/x to reproduce"` — while leaving whitespace-free quoted paths like `".repos/effect"` intact, so a quoted vendored path still denies. The cheap `.repos` early-out runs against `SCAN` too.
    - **The non-git leg does per-shape target analysis, not one "is this write-shaped" flag.** Which token has to be a non-exempt `.repos/` path depends on the shape: a redirect checks its *target* (glued `>file` or the word after a bare operator), `tee` checks the arguments *after* it (tokenized off a `|`-split copy so a glued `echo x|tee .repos/f` still yields a bare `tee` token), `cp`/`mv` check the *destination* operand — clause-scoped on `; & | && ||`, with `-t`/`--target-directory[=]` winning over the last-non-flag-token fallback — and only the operand-mutating set (`sed -i`, `rm`, `patch`, `dd of=`) denies on any `.repos/` token anywhere. The load-bearing consequence: reading or copying **out of** a vendored tree (`cat .repos/effect/src/x.ts`, `cp .repos/effect/src/x.ts /tmp/`) passes, which the earlier any-mention version denied.
    - **Deny messages name the operation.** The git leg's `case` distinguishes unvendoring (`git rm`, `git submodule deinit` → "unvendoring is a lifecycle operation … ask before deleting vendored state") from ordinary vendored-tree writes (→ "re-pin via `repos_manage` action `pin`, sync via `savvy repos sync`, or edit `.repos/config.json` for notes"). A one-size message left agents guessing which sanctioned path applied.

    Three refinements to the git leg are worth understanding as policy, not regex trivia:

    - **The leg engages on "own clause", not just on `-C`/`--git-dir=`/`--work-tree=`.** It fires for any git invocation naming `.repos/` before the next `;`/`&`/`|`, so a bare pathspec form (`git rm --cached .repos/x`, `git mv .repos/x .repos/y`) is now covered too. The clause boundary is the load-bearing part: `git status && rm -rf .repos/x` must NOT let the harmless leading `git` claim the command and route the `rm` through git-subcommand policy — that trailing `rm` still falls to the non-git leg and is denied there. Once the git leg does engage it owns the decision for the whole command, matching the behavior it already had.
    - **`git rm --cached` and `git mv` are sanctioned, `git rm` is not.** Both are index/rename primitives for re-pointing a vendored repo's gitlink, and neither touches vendored *content*: `--cached` is an index-only removal, `git mv` renames the gitlink path in one git-tracked step. They are exactly the recovery moves an agent needs when a submodule path is wrong, so a guard standing in front of them pushes the agent toward a worse workaround. Bare `git rm` (no `--cached`) deletes the working-tree entry and stays denied, as does a bare recursive delete — the line is "mutates the index/pointer" versus "mutates or destroys the vendored tree."
    - **Manifest staging is allowed.** `git add` / `git restore` clear the leg when EVERY `.repos/`-mentioning token in the invocation peels to exactly `.repos/config.json`; a mixed pathspec naming a vendored path in the same call still denies. `.repos/config.json` is host-repo content the agent is expected to edit and commit, so denying the stage step after allowing the edit was pure friction. Subcommand extraction that matches "git targets `.repos/`" but can't confidently name a subcommand fails **open** — ambiguity is not grounds to deny when a permissions layer sits behind the guard.
  - **`repos-mcp-guard.sh`** (same GitKraken/GitHub MCP matcher as `commit-mcp.sh`) denies when the op is in the write set (`git_add_or_commit`, `git_push`, `git_branch`, `git_checkout`, `git_stash`, `git_worktree`, `create_or_update_file`, `delete_file`, `push_files`) and the stringified `tool_input` contains the literal substring `.repos/`. It composes with `commit-mcp.sh` on the same matcher — a deny from either hook wins, so a write op that doesn't target `.repos/` still falls through to `commit-mcp.sh`'s normal flow.
  - Drift the guards miss (or a legitimate command they over-deny) is recoverable through the same sanctioned path they point at: `repos_inspect` to see current state, `repos_manage`/`savvy repos sync|pin` to reconcile it. An agent that hits a false-positive deny should reach for the tool, not a workaround.
- **Preset exclusions.** `.repos/` is excluded from the Biome preset (`packages/silk/public/biome/silk.jsonc`, `+!**/.repos`) and the markdownlint preset (`packages/silk-effects/src/lint/cli/templates/markdownlint.gen.ts` + `lib/configs/.markdownlint-cli2.jsonc`, `+**/.repos`) so a vendored tree's own lint/format drift never surfaces as this repo's problem — consistent with `.repos/**` being read-only reference source, not code this repo owns. The shared tsconfig bases needed no equivalent exclusion: they scope `include` to allowlist globs (`src`, `lib`, `__test__`) that can never reach `.repos/**`, so there was nothing to carve out — a deliberate cut, not an oversight.

## Dogfood-mailbox capability

The plugin's fifth capability is the **dogfood mailbox protocol**: a repeatable loop for two agent sessions in sibling repo checkouts to request, deliver, adopt and iterate on cross-repo changes before anything is released. Its driver is this repo consuming the `@effected/*` kit from a sibling checkout's local prod artifacts via `pnpm-workspace.yaml` `file:` overrides — see the root `CLAUDE.md` "Dogfooding `@effected`" section for the repo-level convention this capability generalizes. It follows the established capability shape (skill + agent-facing enforcement + monitor), with the guard playing the role the `repos` guards do.

- **The `dogfood` skill** (`skills/dogfood/SKILL.md`, `/silk:dogfood --init|--send|--status|--watch|--adopt|--exit`, plus two bundled `references/`) is the protocol itself: mail kinds and their content contracts (`references/mail-kinds.md`), the JSONL journal's snapshot-line shape (`references/jsonl-journal.md`), the phase/ball machine, and the role-aware `--exit`. It is **`paths`-triggered on `**/.claude/dogfood/**`** — a deliberate design point: *reading mail is itself the trigger to act on the protocol*, so the receiving agent gets the journal-append instruction in front of it before it can start treating the mail's content as the more urgent thing.
- **State is a per-loop append-only JSONL journal**, `.claude/dogfood/<counterpart-id>.jsonl`, never edited in place. Current state is the last valid line (no fold/reduce anywhere), history is the file, corrections are appends, and a corrupt tail self-heals because every reader walks back to the last parseable line. Both the guard and the monitor implement that same walk-back independently — it is the contract all three share. Mail lands in the RECEIVING repo at `.claude/dogfood/<sender-id>/`; both the mailbox and the journal are gitignored on both sides. Every append is required to go through `skills/dogfood/scripts/journal-append.sh` (savvy-web/systems#338) rather than a hand-rolled `jq` object — it inherits the last valid line, patches only the passed flags, and validates the event/phase/ball enums before writing; the exact field set (including the three-state `packagesDerived` contract below) is `references/jsonl-journal.md`.
- **`hooks/pre-tool-use/dogfood-guard.sh` — the enforcement half, and the plugin's first *deny* guard outside `repos`.** Registered twice in `hooks.json`: a fifth `matcher: "Bash"` entry and a second entry whose MCP matcher spans both the GitKraken and GitHub MCP servers. It denies `git push` / `gh pr create|edit` (Bash) and, on the MCP side, all five of `git_push`, `pull_request_create`, `create_pull_request`, `update_pull_request` and `push_files`. The decision is keyed on TREE STATE, not journal bookkeeping: it scans only the `overrides:` block of `pnpm-workspace.yaml` (quote-aware comment stripping, so a commented-out override does not trip it) for a `file:`/`link:` path escaping the repo, and denies when one is present on any branch except `dev`, which is exempt unconditionally — `dev` is a long-lived integration branch consumed as compiled bundles, so nothing downstream installs against it. The reason is concrete rather than procedural: a `file:../../` override in `pnpm-workspace.yaml`'s overrides block resolves only on the author's machine, so the hazard is that every other clone, and any CI job that installs, FAILS to resolve the dependency — `pnpm-workspace.yaml` itself is never published. Three boundaries are load-bearing:
  - **No role is guarded — the tree decides, not the journal.** Once the tree is clean of overrides, the journal becomes purely ADVISORY: a downstream journal whose last valid line is in a non-`unlinked` phase over a clean tree downgrades to a WARNING (via `additionalContext`) rather than a deny. The one exception is `packagesDerived: false` on a downstream journal in a non-`unlinked` phase — closure not yet derived is unknown rather than known-clean, so that combination still denies (on any branch but `dev`) even with no override present.
  - **There is no bypass flag** — the explicit lesson of the removed `changeset-push-guard.sh`, whose advertised `SILK_SKIP_PUSH_CHECK=1` remedy taught agents to disarm a repo safety mechanism (see [No hook blocks on changesets](#no-hook-blocks-on-changesets)). A genuinely wrong deny is corrected by appending a `correction` snapshot — the audit trail — not by routing around the hook. That this guard *can* have no bypass is what distinguishes it from the changeset case: "a `file:` override is linked" is a mechanical fact readable from the tree, not a human judgement call, so the guard is never wrong for a legitimate class of branches.
  - **Tripwire posture, same as the `repos` guards** (its header comment says so): best-effort command-string matching rather than a shell parse, fail-open on missing `jq`, a malformed envelope, a non-matching tool, an absent `.claude/dogfood/`, or a journal with no valid line at all — a corrupt journal must never brick every push in the repo, and the guard needs no journal at all to reach its override-based deny decision. All five MCP legs (GitKraken and GitHub) deny, so there is no accepted miss on the MCP side (see [Hook merge](#hook-merge)).
- **`monitors/dogfood-mail.mjs` — the passive half, and the plugin's second background monitor.** A sibling of `watch-issues.mjs` by construction: same self-scheduling poll loop, same pure `diagnose(current, prev)` shape so tests import it without starting the interval, same `--once` mode. It surfaces two local signals — inbound mail files newer than the journal's `lastMail.in`, and a new tail line whose `ball` is `ours`. **Mailboxes are scanned before journals so a turn-flip can be tested against mail the monitor already surfaced** (savvy-web/systems#339): a flip whose `lastMail.in` names mail announced on an EARLIER tick is the local session's own journal append echoing mail it has already been told about, carries no new information, and is suppressed — regardless of which side authored the line, because authorship is not what makes it noise. The comparison is deliberately against the *previous* tick's notified set, not the set being built this tick, so a genuine inbound turn whose mail is being surfaced for the first time still fires both lines. Ordering the two loops is the whole mechanism; there is no extra state. It is **filesystem-only, no network, ever**: the GitHub/registry probes (`gh pr view`, `npm view`) belong to action-time `--status`/`--watch`/`--exit` where a human asked for them and they run under the session's own `gh` auth. A background poller reaching the network on its own schedule is the line this capability does not cross.
- **The it2 transport layer is optional and never authoritative.** When both sessions run in iTerm2 with the `it2` CLI, `--send` rings a doorbell and `--init` can spawn and badge the counterpart session; the file mailbox stays the single source of truth and every feature degrades silently when it2 is absent (headless, SSH, CI). Explicitly **not** adopted: it2's auto-approve/modal plugins — cross-session auto-approval is permission laundering by automation, and approvals stay with the human in each session. That is an on-purpose scope cut, not an oversight.
- **Mailbox content is never design documentation.** `.claude/design/` is the durable record; mail is history. A learning worth keeping past the loop's life gets promoted into a design doc in a normal docs pass, so `.claude/dogfood/` never becomes a second, informal design-doc tree.
- **Claims about an artifact are verified by a stated method, not by instinct.** Handoff precision was already contractual for *signatures* (read from the built `.d.ts`, never from source or memory); the skill now extends the same discipline to *presence*: search recursively (`rg <symbol> <dir>`, never a non-recursive `<dir>/*.js` glob — a `@savvy-web/bundler`-style per-module chunk layout puts the symbol in a nested path a top-level glob cannot see), cite the module path rather than a match count (a path the counterpart can check, a count they cannot), and grep a known-present control symbol before reporting one as absent. API-surface claims prefer the published `.d.ts` or the `exports` map, since chunk layout is a build-tool detail. This is written as settled protocol because the same non-recursive-glob mistake produced a false "the fix is missing" twice in one round from two different sessions — the cost is a spurious rebuild request and a retraction, and the fix is a method, not more care.
- **A relay owes its downstream a `status`.** When this repo is simultaneously downstream in one loop and upstream in another over the same change, a milestone in the upstream loop IS a milestone in the downstream loop: the counterpart holding a `file:` link against this repo's build has no other way to learn the tree is mid-migration. The skill names the three moments (the upstream counterpart ships, adoption starts, the tree is safe to build against again), making `status` the relay's notification vehicle rather than a purely local courtesy.
- **A closed loop reopens through `briefing`, not a new kind.** A journal that ended on a terminal `unlinked` line and later gets a fresh non-`unlinked` `loop-started` append boots the counterpart with a `briefing` — that session is starting from nothing and needs the same mailbox/journal/role/push-guard content it would on round 0. Only the framing differs: a reopen briefing carries the CURRENT round number (never `round: 0`) and opens with the prior loop's terminal state before the standard boot content. This keeps one boot path instead of a second near-duplicate kind.

Testing: the guard and the monitor are covered by bats plus PreToolUse fixtures; `plugins/*/tests` (run by `pnpm test:hooks`) is the authoritative count, not a number transcribed here.

## it2 pane-orchestration capability

The plugin's lightest capability teaches the agent to orchestrate iTerm2 panes and windows for the subagents it spawns via the separately-installed `it2` CLI. It follows the same *gated orientation nudge + point-of-use skill* shape as `turbo`/`repos`/`tsdoc`/`dogfood`, but is the leanest instance of it — a skill and a conditional orientation block, with **no** agent, MCP tool, hook or guard. It is the proactive successor to the former always-on cleanup-only `<terminal>` block (savvy-web/systems, 2026-07-21 design).

- **The gated `<terminal>` orientation block** (in `hooks/session-start/orientation.sh`, part of the `<silk_capabilities>` payload — see [MCP tool orientation](#mcp-tool-orientation)) renders only when the env-only gate holds: `(TERM_PROGRAM == "iTerm.app" OR LC_TERMINAL == "iTerm2") AND command -v it2`. The gate is deliberately **prompt-free** — it runs no it2 subprocess, because the hook fires on every resume/compact and any it2 call risks its first-use iTerm2 API-authorization dialog or a hang. A false-positive (it2 on `PATH` but the API not yet authorized) is self-correcting: the first point-of-use call triggers the auth prompt, which the agent surfaces to the user; a false-negative (iTerm2 not exporting `TERM_PROGRAM`, e.g. some SSH/tmux nesting) is a missed nudge, never a broken session. The block is index-shaped: a proactive posture (split and badge a pane per subagent, manage windows on the user's behalf while keeping them legible, match split direction/grid to window geometry) plus the dismiss-and-close discipline, pointing at `/silk:it2` for depth.
- **The `it2` skill** (`skills/it2/SKILL.md`, `/silk:it2`, model- and user-invocable, description-triggered, **no** `paths` trigger since it has no backing file) is the self-contained playbook — it drives the raw `it2` CLI and does **not** depend on the external `it2-skills` marketplace plugin. It carries the pinned split-direction semantics (`--vertical` = new pane right, `--horizontal` = new pane below, no-flag = auto) with the inversion warning, the geometry-driven layout heuristic table (portrait → stack, landscape → side-by-side, many → grid, multi-window/monitor → spread), point-of-use geometry queries (`it2 window list --format json`, `it2 session get-info <sid> --format json --extract grid_size`), grid recipes (the "new pane is adjacent to the session being split" caveat, `--before`, `session move`), the session-id-prefix badging convention, the dismiss-and-close discipline, and a "when NOT to orchestrate" guardrail (single trivial dispatch, no parallelism asked for, headless) so proactive never becomes intrusive. All geometry queries and every it2 call happen at point-of-use, never in a hook.

Its relationship to the `dogfood` capability's optional it2 transport layer (see [Dogfood-mailbox capability](#dogfood-mailbox-capability)) is a clean division: `dogfood` uses it2 as a cross-session *doorbell/spawn transport*, this capability uses it2 as a *pane-layout tool for subagents* — same CLI, different job. Both deliberately decline it2's auto-approve/modal plugins: cross-session auto-approval is permission laundering, and approvals stay with the human in each session.

## Commit and PR message capability

Two authoring skills — `commit-create` and `pr-body` — plus the `savvy commit hook pre-commit-message` guard they share. The organizing decision is that **the commit message and the PR description are one editorial system with a division of labor**, not two independent formats.

- **The division of labor splits on document, not on command.** Anything that is or becomes a conventional-commit subject — the commit message, the PR title, the contents of a `proposed-squash-commit` fence — is `commit-create`'s; the PR description prose is `pr-body`'s, and is explicitly not held to the commit contract. Because `gh pr create --title` and `--body` are one command spanning both documents, a single invocation routinely needs both skills, so activation triggers keyed on commands rather than documents make the two skills claim the same work and give opposite guidance. That is exactly how `commit-create` shipped with PR-description triggers after `pr-body` was added (PR #420).
- **Depth belongs in the PR, not the commit.** This repo squash-merges, so a long commit body is discarded at merge and the PR description is what survives. `commit-create` therefore teaches a hard shape — a few bullets or one to two short paragraphs — and `pr-body`'s summary region is where reasoning, evidence and migration guidance go. The silk-effects `verbosity` rule's thresholds are sized to that shape and move with it (see `../silk-effects/architecture.md`); the skill's prose and those constants are a coupled pair.
- **The `commit-create` format is calibrated against what the preset actually enforces, not against what it looks like it might.** Dash bullets are legal (the `silk/body-prose-only` rule is never enabled by `createConfig`, and `detectMarkdown`'s bullet pattern is defined but never tested), and multiple issues go on one comma-separated `Closes` line rather than several lines — which is why the `closes-trailer` rule has to scan the whole reference list. Verify a claim about the preset against the rule source before writing it into the skill; the skill's authority is that it matches the enforcing code.
- **The skill's `validate-message.sh` reproduces the hook's parse, so its silence has to mean the same thing.** The blank-line-separated subject / body / `Closes` / signoff layout the skill teaches meant the script's backward footer scan stopped at the blank line and measured a long `Closes` line against the body's character cap instead of the footer's, staying silent on a message the commit-msg hook then rejected. A pre-flight validator that disagrees with the gate is worse than none, so the scan crosses a blank line when a trailer precedes it.
- **`pr-body` documents a marker contract, not a template.** A release PR description has several writers — the release action regenerates its managed region on every push, humans type above it, agents write into it — and HTML-comment markers are the whole mechanism keeping them apart. The skill's job is to say which regions the agent owns (`silk-release:summary`, carried through), which are rebuilt wholesale, and that a `proposed-squash-commit` fence is a commit message subject to `commit-create`. The `silk-release:references` region and its `owned` attribute come from the sibling `savvy-web/silk-release-action` repo and are not yet merged there; the skill is the consumer-side half of that contract.
- **The two `Closes` spellings are deliberate and both load-bearing.** Comma-joined on one line inside the fence, because that is a commit message and commitlint reads it; one bare `Closes #N` per line outside the fence, because GitHub's issue linker reads only that form and a reference inside a code fence is inert. Neither can be normalized to the other.
- **The hook is registered on `gh pr create`/`pr edit` as well as `git commit`, and gates its rules on which.** The canonical release PR body opens a fenced block, which the `forbidden-content` rule denies outright, so applying commit-body rules to a PR body blocked posting the ecosystem's own generated description. The gate lives in the CLI hook handler — see `../cli/architecture.md`.

## The config skill drives changeset_inspect

The `config` skill (`skills/config/SKILL.md`, agent-internal, `user-invocable: false`) is the `changeset-manager` agent's window onto changeset attribution. It calls the shared `savvy-mcp` server's `changeset_inspect` MCP tool directly (`allowed-tools: mcp__plugin_silk_savvy-mcp__changeset_inspect`), with `mode: "branch"` as the primary create-mode classification call and `mode: "config"` as the secondary config-only view (a third `mode: "classify"` resolves an arbitrary path to its owning package). The `changeset-manager` agent holds the same `changeset_inspect` grant plus `changeset_validate` (post-write changeset-file validation), `changeset_preview` (release preview before deciding whether more changeset work is needed) and the `changeset_deps_regen`/`changeset_deps_detect` grants the `dependencies` skill drives, and reads the tool's `structuredContent` (the `BranchAnalysis` / `InspectedConfig` shapes); the `dependencies` skill's "when to invoke" check reads the same `mode: "branch"` result. Its `tools:` frontmatter also carries `Bash(bash *)` so it can run the router's bundled `list.sh` directly during inventory. See `../mcp/architecture.md` for the tool half.

The load-bearing reason it uses the MCP tool rather than the CLI: the CLI's `--json` output is prefixed with an `Effect.log` `[…] INFO (#NN):` line that breaks a naive `JSON.parse` of stdout. The structured MCP result has no such framing, removing the stdout-parsing fragility. Error handling also simplifies — the tool surfaces `ConfigurationError` / `GitError` as MCP tool errors (no exit codes, no stderr to parse), and there is no "CLI not installed" branch because the MCP server ships the implementation. The `savvy changeset analyze-branch` / `config show` / `classify` / `release-surface` inspection commands have been **removed** from the CLI; the `changeset_inspect` / `changeset_validate` MCP tools are the inspection surface. The CLI keeps only `lint` / `validate-file` (used by the bash PostToolUse hook) plus `check` / `transform` / `version` / `config validate` / `deps`.

The `/silk:changeset --preview` router mode is the read-only release-preview front door: it renders directly from the `changeset_preview` MCP tool, which runs the genuine changesets engine and returns the version bumps plus rendered CHANGELOG blocks. There is no hand-rolled CHANGELOG-merge step — the router presents the tool's structured result and markdown transcript, with the only caveat narrowed to the inherent commit-metadata gap. See `../mcp/architecture.md` for the tool and [Changeset command surface](#changeset-command-surface) for the router.

## Hook merge

All source hook sets merge into `plugins/silk/hooks/hooks.json`. PreToolUse/PostToolUse matchers combine across the commitlint bash/fs/mcp guards, plus the Biome `biome-prefer-mcp.sh` nudge as a second `matcher: "Bash"` PreToolUse entry and `biome-direct-deny.sh` as a third `matcher: "Bash"` entry immediately after it (see [Biome capability](#biome-capability)), the three vendored-repos guards — `repos-fs-guard.sh` as a third leg on the `Write|Edit|NotebookEdit` matcher, `repos-bash-guard.sh` as a fourth `matcher: "Bash"` entry, and `repos-mcp-guard.sh` as a second entry on the commitlint MCP matcher (see [Vendored-repos capability](#vendored-repos-capability)) — and `dogfood-guard.sh`, registered twice: a fifth `matcher: "Bash"` entry and an MCP entry spanning both the GitKraken and GitHub MCP servers (`mcp__(gk|gitkraken|GitKraken)__.*|mcp__github(-[^_].*)?__.*`), the same span the `commit-mcp.sh`/`repos-mcp-guard.sh` matcher uses. See [Dogfood-mailbox capability](#dogfood-mailbox-capability). A single `Stop` hook, `stop/changeset-nudge.sh`, carries the changeset reminder (see [No hook blocks on changesets](#no-hook-blocks-on-changesets)). Every hook script targets the unified `savvy changeset …` / `savvy commit hook …` paths; the shared resolver in `hooks/lib/` targets the single `savvy` bin.

A standing hygiene concern is avoiding double-fires where multiple guards share a matcher (`Bash`, `Write|Edit|NotebookEdit`, or the commitlint MCP regex) — check `hooks.json`'s matcher set when adding a new guard on any of them.

The same applies to the **skill scripts**: any bundled script that shells out to the Silk CLI goes through the single `savvy` bin — no script may assume a per-tool `savvy-*` bin is installed. The changeset router's one bundled script, `changeset/scripts/list.sh` (the `--list` mode), is a deliberate exception to *which* CLI it targets: it shells out to the project's own `@changesets/cli` (`changeset status --output`) for structured JSON, not to `savvy`. Validation no longer rides a CLI script at all — the router's `--check` mode calls the `changeset_validate` MCP tool directly (see [Changeset command surface](#changeset-command-surface)).

The `config` and `dependencies` skills are the exceptions: neither shells out — `config` calls the `changeset_inspect` MCP tool directly (see [The config skill drives changeset_inspect](#the-config-skill-drives-changeset_inspect)), and `dependencies` calls the `changeset_deps_regen`/`changeset_deps_detect` MCP tools directly (its former `detect.sh`/`regen.sh` scripts are retired). Both are thin adapters over `Changesets.DepsRegen` — see `../mcp/architecture.md` and `../silk-effects/architecture.md`.

### SessionStart: three hooks, split by responsibility

Three SessionStart hooks are registered as three entries in `hooks.json`, split by *when* they fire and *what side effect* they own:

- `session-start/orientation.sh` — **no matcher**, so it fires on every start including resume and compact. It is the env **producer**: it detects the package manager, writes the session vars and dedup-appends them to `$CLAUDE_ENV_FILE` (see the namespace note below). It also emits the always-on `<silk_capabilities>` block — the compact MCP tool, agent and skill indexes plus the three-line Biome division of labor and the prose active-hooks note (see [MCP tool orientation](#mcp-tool-orientation)). The block as a whole is always-on, but its `<terminal>` sub-block is the one conditional entry: an env-only, prompt-free iTerm2+it2 gate (no it2 subprocess in the hook) decides whether it renders (see [it2 pane-orchestration capability](#it2-pane-orchestration-capability)).
- `session-start/startup-only.sh` — **`matcher: "startup"`**, so it fires only on a fresh start, not resume or compact. It runs the `savvy commit hook session-start` side effect (stdout redirected so it cannot pollute the hook JSON) and emits the edit-time contract: a brief Silk-system intro, the blocking lint rules, the `<pre_commit_pipeline>` block naming every lint-staged autofix (including the intentional exec-bit strip on `.sh` files), and the LSP-first `<running_tools>` preference order. (Design-doc-agent orientation is owned by the design-docs plugin, so silk intentionally does not duplicate it.) Because a SessionStart hook cannot block, its missing-`CLAUDE_PROJECT_DIR` guard emits a noop and exits 0 rather than failing the session.
- `session-start/repos-orientation.sh` — **no matcher**, so like the producer it fires on every start including resume and compact, but it is unconditional on a *different* axis: it self-silences (a single `emit_noop`) whenever `.repos/config.json` doesn't exist, which is the common case for a session outside a repo that vendors reference repos. See [Vendored-repos capability](#vendored-repos-capability) for the sync-watchdog/reap and 2000-char-budget detail.

### Session env namespace: `SILK_*`

The producer writes the `SILK_*` session vars (project dir, data dir, plugin root, session id, package manager) to a per-session `silk-hook.sh` file under `~/.claude/session-env/${session_id}/`. The lateral-propagation helper `hooks/lib/source-session-env.sh` sources every `*hook*.sh` in that dir, so consumer hooks (the changeset-validate post-tool hook, the Stop nudge) and the changeset skill scripts pick the vars up by their `SILK_*` names. The nudge opt-out is `SILK_SKIP_CHANGESET_NUDGE` and the debug toggle sourced from `hooks/lib/hook-debug.sh` is `SILK_HOOK_DEBUG`.

**`SILK_PROJECT_DIR` is not a project-dir override.** It is derived from `CLAUDE_PROJECT_DIR` by the SessionStart producer, so it carries the same value and the same limitation: it names the session's **primary checkout**, and does not track the directory an individual tool call runs in. Hooks that reason about git state must resolve the tree from the hook envelope's `cwd` — see [Working-tree resolution](#working-tree-resolution).

### Working-tree resolution

`hooks/lib/hook-env.sh` is the single place hooks resolve two things: the stdin envelope (`read_envelope_or_noop` — validates the JSON and no-ops on garbage rather than aborting under `set -euo pipefail`) and the working tree (`resolve_project_dir`).

`resolve_project_dir` takes the envelope's `cwd` **first**, then `SILK_PROJECT_DIR`, then `CLAUDE_PROJECT_DIR`. That order is load-bearing. Both env vars are pinned to the primary checkout for the whole session; only `cwd` follows a git worktree. Since agents routinely work in worktrees (`.claude/worktrees/agent-<id>/`, on their own branch, at their own commit), a hook that resolves git state from either env var is inspecting a tree with no relationship to the call it is handling. Ranking `SILK_PROJECT_DIR` above `cwd` — its name invites this — silently reinstates the bug in every real session, because the SessionStart producer always writes it.

### No hook blocks on changesets

Whether a change needs a changeset is a **human judgement**, and the plugin's hooks do not make it. A hook can only see "commits exist, no `.changeset/*.md`", which cannot distinguish a user-facing fix from a docs-only branch — so any hook that *blocks* on that signal is guaranteed to be wrong for a large, legitimate class of branches (docs, CI, tests, internal refactors).

The previous `pre-tool-use/changeset-push-guard.sh` did block, and it was removed rather than repaired (savvy-web/systems#274). Two failures drove that:

- **It was unsound.** It resolved its tree from `CLAUDE_PROJECT_DIR`, so it judged worktree pushes against whatever branch the primary checkout happened to be on — denying pushes whose changesets were present, and waving through pushes it never evaluated. Its verdict depended on the caller's cwd, not on the ref being pushed.
- **Its remedy was a safety bypass.** The deny message advertised `SILK_SKIP_PUSH_CHECK=1`, so an agent following the guard's own instructions attempted to disarm a repo safety mechanism — which Claude Code's safety classifier then flagged. A guard that misfires teaches the thing it guards to route around it, and this escape hatch was the worst possible one to make habitual.

What replaces it:

- **`stop/changeset-nudge.sh`** (Stop) emits a top-level `systemMessage` — shown to the **user**, not injected into the model's context — when the branch has commits and no changeset. It emits no `decision` and no `additionalContext`: it cannot block the stop and does not ask the agent to act. `Stop` fires only for the main agent (`SubagentStop` is a separate event), so a subagent making many commits is never nagged. It is debounced on HEAD, so it speaks once per commit state rather than once per turn.
- **CI on the pull request** is where enforcement lives: the full branch diff is available there, and an override is an explicit, reviewable human act.

Commit time is deliberately *not* a nudge point: the changeset decision needs the whole branch diff, which does not exist at commit 3 of 12.

### Canonical lib, no per-plugin duplicates

Every hook sources the canonical `hooks/lib/hook-output.sh` and `hook-debug.sh`; there are no per-tool duplicates of these libs.

### Hook scripts carry no exec bit

Hook scripts commit as `100644`: the lint-staged ShellScripts handler strips the executable bit from staged `.sh` files, and nothing needs it — every hook is invoked as `bash "${CLAUDE_PLUGIN_ROOT}/hooks/..."` by `hooks.json` and the bats runner. Reviews keep flagging new 644 scripts against older 755 siblings as accidental mode drift; it is intentional normalization, not a bug (savvy-web/systems#289). The same note lives in `plugins/silk/tests/README.md` and `lib/configs/lint-staged.config.ts`.

### Dogfood-feedback prompt (removed)

Unrelated to the [Dogfood-mailbox capability](#dogfood-mailbox-capability) despite the shared word — that is a cross-repo collaboration protocol; this was a prompt about reporting rough edges in the plugin itself.

Early releases carried an always-on dogfood-feedback prompt (note rough edges, ask the user before filing issues). It was removed from the orientation payload once the plugin matured past its initial dogfooding phase: it cost ~700 characters of every context window — including after every resume and compact — long after "newly released" stopped being true. Rough-edge reporting still happens organically; the hard user-agreement gate on issue filing remains the norm for agents regardless of any prompt.

## Rationale

### Why one plugin, prefixed skills

In practice the three tools are installed and configured as a unit, and a consumer wants one plugin, not three. Merging them removes per-plugin ceremony. Tool-prefixing the user-facing skills is what makes a single merged skill namespace legible; the agent-only mechanics stay unprefixed because no human types them.

### Why hooks target the single savvy bin

The point of the merge is one bin. Hooks that still shelled out to per-tool `savvy-changesets` / `savvy-commit` bins would defeat the merge and require the old packages installed. Targeting `savvy changeset …` / `savvy commit hook …` makes the plugin self-consistent with the merged CLI.
